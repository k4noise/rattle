# Rattle

Разрабатываемый сервис для проверки HTTP API некорректными запросами по OpenAPI-схеме. При ошибке целевого сервера сервис старается уменьшить упавший запрос до короткого воспроизводимого примера, который всё ещё вызывает падение.

**Сейчас реализованы парсер OpenAPI, генерация некорректных запросов и их последовательная HTTP-отправка.** Минимизация и REST API — в планах.

## Парсер OpenAPI

`OpenAPIParser.parse(raw_spec: str | bytes) -> OpenAPISpec` принимает JSON или YAML; байты декодируются как UTF-8. Результат содержит `spec.endpoints` с `method` и `path`, а также `spec.warnings`. Экземпляр парсера можно использовать повторно, в том числе после ошибки входных данных.

### Чтение JSON и YAML

- Повторяющиеся ключи отклоняются во всём документе. JSON с `NaN`, `Infinity` или числами, переполняющими `float`, не принимается.
- YAML читается по скалярным правилам YAML 1.2 Core и ограничен JSON-совместимыми значениями со строковыми ключами. `yes`, `on` и даты остаются строками; не-JSON теги и неконечные числа отклоняются. `<<` считается обычным ключом, а не объединением словарей.

### Поддерживаемое подмножество

- OpenAPI `3.0.x` и `3.1.x`; методы `GET`, `POST`, `PUT`, `PATCH`, `DELETE`.
- Параметры `path`, `query`, `header`, `cookie`. Параметры операции переопределяют параметры пути; имена заголовков сравниваются без учёта регистра. Header-параметры `Accept`, `Content-Type`, `Authorization` игнорируются с предупреждением; схемы авторизации пока не обрабатываются.
- Тела `application/json` и `application/*+json`; при наличии обоих выбирается обычный JSON.
- Локальные `$ref`, в том числе на схемы, параметры и тела запросов. Поддерживаются percent-encoding в URI-фрагменте и экранирование `~0`/`~1` в JSON Pointer.
- Объекты, массивы, примитивы и ограничения `enum`, `required`, `minimum`/`maximum`, `minLength`/`maxLength`, `pattern`, `format`. Целые числовые границы сохраняются без преобразования во `float`.
- `nullable`, тип `[T, "null"]`, `anyOf` из типа и `null`, одиночная обёртка `allOf`. При свёртке `anyOf` с отдельной ветвью `null` он добавляется в существующий `enum` другой ветви, если его там ещё нет; без enum новый не создаётся. Например, `anyOf: [{type: "null"}, {type: string, enum: [x]}]` разрешает `x` и null; `type: [string, "null"], enum: [x]` разрешает только `x` — общий enum не расширяется.

Если `type` отсутствует, схема остаётся типом `any`: наличие `properties` или `items` не превращает её в объект или массив. У path-параметра пропущенное `required` считается `True`, а явно заданное `False` — ошибкой.

Парсер извлекает данные для фаззинга, а не полностью валидирует OpenAPI: например, он не требует `info.version` и не проверяет `responses`.

### Сериализация параметров

Для query и cookie парсер задаёт `style=form`, `explode=True`; для path и header — `style=simple`, `explode=False`. Явное `explode` сохраняется. `allowReserved` сохраняется как `allow_reserved`, но значение `True` допустимо только для query.

Другие стили (`deepObject`, `spaceDelimited`, `pipeDelimited`, `matrix`, `label`) и `allowEmptyValue: true` отклоняются, а не теряются при разборе. Поддержка конкретных HTTP-представлений описана ниже.

### Ограничения и ошибки

- `HEAD`, `OPTIONS`, `TRACE` и не-JSON тела пропускаются с сообщением в `spec.warnings`. Если поддерживаемых операций нет, разбор завершается ошибкой.
- Внешние ссылки, URI-якоря вместо JSON Pointer, boolean-схемы, общий `oneOf`/`anyOf`, многоветочный `allOf`, другие объединения типов и неподдерживаемые ограничения, например `additionalProperties`, вызывают `InvalidOpenAPISpecError`. Ограничения рядом с `$ref` или поддерживаемой композиционной обёрткой тоже отклоняются.
- Аннотации, `default`, примеры, `readOnly`/`writeOnly` и `x-*` не влияют на модель. `pattern` и `format` сохраняются, но значения по ним пока не проверяются.
- Рекурсивное поле получает `SchemaSpec(is_recursive=True)`; цикл чистых алиасов — ошибка. Повторное использование схемы в соседних полях циклом не считается.
- Глубина схем, цепочек ссылок и вложенных значений `enum` ограничена 64 уровнями; бюджеты посещений схем и значений `enum` — по 10 000 на документ. Значения `enum` должны быть JSON-совместимыми и не содержать циклов.
- Значения ограничений проверяются, но их совместимость между собой и с `enum` — нет. Успешный разбор не гарантирует, что схеме соответствует хотя бы одно значение.

### Контракт моделей

Модели `frozen`, но вложенные коллекции изменяемы: для мутации запросов данные нужно копировать. Равенство моделей — обычное сравнение dataclass и Python-значений, не семантическое сравнение JSON Schema; хешируемость не гарантируется.

## Генерация запросов

`RequestGenerator` принимает `EndpointSpec` из парсера. `build_base(endpoint)` строит базовый пример, а `generate(endpoint, limit=100)` лениво выдаёт варианты `MutationCase` с одной локальной мутацией. Генератор работает с данными запроса; HTTP-представление и отправка — отдельный этап.

### Базовый пример

- Генератор учитывает поддерживаемые типы, `any`, `nullable`, `enum`, обязательные значения и границы чисел и строк. Из `enum` выбирается первое значение, подходящее под остальные ограничения. Пример соответствует поддерживаемой модели, но не обязательно бизнес-правилам API.
- Для объектов заполняются описанные поля; для массивов с `items` строится один элемент. Невыполнимые необязательные значения пропускаются с предупреждением `omitted_optional`. Если элемент массива построить нельзя, массив может остаться пустым с предупреждением `empty_array`. Для обязательного значения без подходящего примера возникает `NoExampleError`.
- `RequestData` хранит метод, шаблон пути, типизированные параметры, JSON-тело и `warnings`. Поле `has_body` отличает отсутствие тела от явного JSON `null`. Параметры сохраняют `style`, `explode` и `allow_reserved`; URL, заголовки и байты тела формирует сериализатор.

### Мутации

Доступны удаление обязательного значения (`missing_required`), замена на неверный тип (`wrong_type`), выход за `enum` (`outside_enum`), числовые границы (`below_minimum`, `above_maximum`) и границы длины строки (`too_short`, `too_long`).

У `MutationCase` есть `kind`, `location`, `path` и `request`. `path` — кортеж имён полей и индексов массива; `()` обозначает корень тела. Варианты независимы друг от друга и идут в воспроизводимом порядке: сначала параметры, затем тело. Одинаковые итоговые запросы пока не дедуплицируются.

Удаление path-параметра убирает его значение из данных, но оставляет путь шаблоном, например `/items/{id}`. Отправитель возвращает `unsendable`: сегмент не удаляется, `None` и сам шаблон в URL не отправляются.

### Ошибки и лимиты

Ошибки наследуют `RequestGenerationError`:

- `UnsupportedSchemaError` — неподдерживаемая возможность, в том числе `pattern`, `format` или рекурсивная схема.
- `NoExampleError` — не удалось построить обязательное значение.
- `GenerationLimitError` — превышен лимит глубины, работы или длины строки.

По умолчанию `RequestGenerator(max_depth=32, max_nodes=100_000, max_string_length=4096)` ограничивает один вызов генерации. `limit=0` не запускает обход схемы. Поскольку варианты выдаются лениво, ошибка может возникнуть во время итерации; повторный вызов получает новый бюджет.

## Отправка запросов

HTTPSender из rattle.sending используется только через with. send(case) отправляет один вариант, send_all(cases) лениво и последовательно обходит варианты. Базовый URL задаётся явно, его префикс пути сохраняется. Запросы действительно выполняются и могут менять состояние целевого API.

SendResult содержит исходный case, снимок подготовленного запроса request, response, error, результат проверки доступности availability и outcome: response, crash, unsendable, serialization_error или network_error. is_crash — признак падения. Снимок не доказывает доставку серверу; при ошибке до отправки request=None.
Сериализация и ограничения

    RequestSerializer(base_url).serialize(data) из rattle.serialization работает без сети. Поддерживаются simple для path и header, form для query и cookie, примитивы, плоские массивы и объекты, explode и allow_reserved для query. Значения заголовков передаются без percent-encoding, в Latin-1. Тело кодируется как JSON; отсутствие тела не подменяется null.
    Исход unsendable получают запросы с отсутствующим path-параметром, с null или вложенной коллекцией в параметре, с пустой exploded-коллекцией в query или cookie, а при allow_reserved=True — с &, +, #, ; в значении или с запятыми в элементах и ключах коллекции при explode=False. Некорректные JSON, URL и заголовки дают serialization_error. При прямом вызове сериализатора возникает RequestSerializationError или его подкласс UnsendableRequestError.
    Заголовки, которыми управляет клиент (Host, Content-Length, Content-Type и другие), нельзя задавать как header-параметры.
    Лимиты по умолчанию: запрос — 1 МиБ (max_request_bytes), сериализация — 100 000 узлов и 64 уровня; от ответа сохраняется до 64 КиБ (max_response_bytes) без распаковки Content-Encoding. truncated=True означает обрезку по лимиту, complete=False — недочитанное тело. timeout и availability_timeout задаются в секундах для фаз HTTPX, а не для всей проверки.
    Отправитель одноразовый и не потокобезопасный. Он не повторяет запросы, не переходит по redirect, не переносит cookies между вариантами, не использует прокси из окружения и не настраивает авторизацию.

Классификация и доступность

    Статус 5xx — падение, даже если чтение тела затем прервалось. 4xx падением не считается.
    Обрыв уже начавшегося ответа (статус и заголовки получены, тело не дочитано) считается падением, только если после него успешна проверка доступности. Обрыв — это ReadError при чтении тела или RemoteProtocolError при фактическом EOF соединения (response.peer_eof).
    Ошибки чтения до получения ответа, таймауты, ошибки соединения и RemoteProtocolError без подтверждённого EOF, например некорректная строка статуса (error.kind="protocol"), остаются network_error.
    Проверка доступности — GET по availability_url: явно заданному безопасному адресу того же origin. Полный ответ с любым статусом подтверждает только сетевую доступность. Без availability_url обрыв падением не считается.
    После max_unavailable сетевых сбоев подряд без подтверждения доступности возникает TargetUnavailableError из rattle.exceptions с последним результатом в last_result; следующий вариант не извлекается. Счётчик сбрасывают ответ без транспортной ошибки, 5xx и успешная проверка доступности; ошибки данных его не меняют. После остановки отправку продолжить нельзя; использование вне активного with даёт SenderStateError.

## REST-эндпоинты (план)

- `POST /jobs` — запустить проверку.
- `GET /jobs/{id}` — статус и прогресс проверки.
- `GET /jobs/{id}/crashes` — список найденных падений.
- `DELETE /jobs/{id}` — остановить и удалить проверку.
- `GET /docs` — Swagger UI.

## Выбор коллекций

- `list` — промежуточные эндпоинты, параметры и предупреждения в порядке разбора, JSON-массивы; позже — падения и шаги уменьшения запроса.
- `tuple` — итоговые параметры и эндпоинты, путь к месту мутации, хешируемый ключ параметра; позже — ключ ошибки `(метод, путь, код ответа)`.
- `dict` — документ OpenAPI, свойства объектов, объединённые параметры и JSON-объекты запросов; позже — проверки по `id`.
- `set` — поиск дубликатов параметров и циклов ссылок; позже — отсев повторных падений.
- `frozenset` — обязательные поля и активные ссылки в отдельной ветви рекурсии.
